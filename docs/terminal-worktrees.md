# Worktrees: an agent's own checkout on the machine

A worktree request asks a machine to give an agent its own git worktree and branch
before it starts the agent, so that agents started together never share a
checkout. It is an optional pair of fields on the launch request described in
[Launch requests](terminal-launch.md), plus two further requests: one that reports
what is in a run's worktree and one that removes it. reet never removes a worktree
by itself, and never deletes the branch.

This document describes what the code does after the commits "Offer worktrees
through the broker and API" and "Refuse removal for nested bare repositories and
make the partial-scan refusal tested" in Projects PR 1. The controller side
that calls it (the Project store, the Projects API and the run orchestration) is
Projects PR 2; see "The run orchestration" below. What people see, the Projects
routes and the *Remove worktree* dialog are in [Projects](projects.md).

## Negotiation

After authenticating an agent, the private control upgrade now advertises
`X-Reet-Terminal-Features: command-history-v1,launch-v1,worktree-v1`. A connector
that understands `worktree-v1` records it; an older one ignores the token and
connects unchanged.

A connector reports the capability `worktree:true` only when all of these hold:
it reports `launch` (so terminal control, a tool lister, and Linux or macOS),
`worktree-v1` was negotiated, and `git` is found on its `PATH` at an absolute path.
`worktree` cannot be set without `launch`. The capability reaches
`/api/v2/terminal/machines` and `/api/v2/machines/health` as
`capabilities.worktree`, and is omitted for a machine without it.

The controller checks the stored capabilities for the current connection
generation before it sends any worktree field or request. A machine without
`worktree` is never sent one, nothing is reserved, and the API answers 409
`worktree_unsupported`: "Update reet on that machine to start agents with
worktrees." The connector also refuses on its own side: a create carrying a
worktree on a connection that did not negotiate `worktree-v1` is answered
`launch_failed` and no agent starts; a status or remove is answered `denied`.
There is no protocol version bump.

Mixed versions are compatible. `worktree` and `project` are omitted from every
create that does not ask for a worktree, and a controller sends them, and the
status and remove requests, only to a connection that negotiated `worktree-v1`.
The new reply fields (`worktreePath`, `worktreeRepo`, and `path` and `branch` on
a remove's answer) are only ever sent in answer to those new requests, so an older
controller never receives them. Both sides still decode strictly: a connector
refuses a message with a field it does not know, which is why nothing new is sent
to a connector that did not ask for it.

## Wire fields

`terminalproto.Create` gains two flat optional strings, so it stays a comparable
struct and a plain or launch-only create encodes exactly as before:

| Field | Meaning | Rules |
| --- | --- | --- |
| `worktree` | Run token | Lower-case hex, 16 to 48 characters. Requires `tool`, `dir` and `project`. |
| `project` | Project slug | 1 to 40 bytes of `a-z`, `0-9` and single hyphens between words. Allowed only with `worktree`. |

The run token is chosen by the caller, never generated by the controller: a
retried request must carry the same token so the machine adopts the worktree it
already made. The Projects run (PR 2) derives it from the run.

Two requests, `worktree_status {run, project, repo}` and `worktree_remove {run,
project, repo, changed, unpushed}`, are answered by `worktree_state` or
`worktree_result {code, reason, detail}`. `repo` is the repository folder's name
on the machine: 1 to 100 letters, digits, `.`, `_` and `-`, never `.`, `..` or a
leading `-`. None of these messages is bound to a session.

The reply to a worktree create, `session_changed`, gains two flat optional strings
set together: `worktreePath` (the folder the machine made or adopted) and
`worktreeRepo` (the repository name, as the machine slugged the resolved folder's
name, which is what status and remove take). The connector keeps them in its
registry entry for the session, so a replay of the same create reports them again.
They are never set on any other session change.

## Where worktrees go

- Folder: `~/.reet/worktrees/<project>/<repo-slug>/<run>`, where `~` is the
  machine's home with symlinks resolved and `<repo-slug>` is the slug of the
  resolved repository folder's name (lower-case letters, digits and hyphens; a
  name longer than 40 bytes keeps its start plus 8 hex digits of its SHA-256).
- Branch: `reet/<project>-<run>`, made at the repository's current `HEAD`.
- Folders reet makes are mode 0700. Every folder from home down to the
  destination must be a real directory owned by the user and not writable by group
  or others; a symlink, a file, another owner or a writable folder is refused as
  `outside_home`. An existing `~/.reet` with mode 0755 is accepted.

## The git commands

git is always run as an argument vector, never through a shell, with an empty
stdin, `-C <folder>` rather than a working directory, and an environment of exactly
`HOME`, `PATH` and `LANG` (the first of each); every `GIT_*` variable and every
other variable is removed. git is looked up on `PATH` on every call and must be at
an absolute path.

### Creating

In the repository folder, in this order (the folder must already pass the launch
folder rules: absolute, inside home, symlinks resolved):

1. Without git: `.git` must be a real directory (not a file, not a symlink), the
   repository must not contain `~/.reet`, and none of `MERGE_HEAD`,
   `rebase-merge`, `rebase-apply`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`,
   `BISECT_LOG` or `sequencer` may exist in `.git`.
2. `git rev-parse --show-toplevel`, which must equal the folder.
3. `git rev-parse --verify --quiet HEAD^{commit}`, which must name a commit.
4. `git for-each-ref --format=%(refname) refs/heads/reet/<project>-<run>`.
5. `git worktree list --porcelain`.
6. `git -c core.hooksPath=/dev/null worktree add -b <branch> <destination> HEAD`,
   the only command that changes anything when all goes well. With a named
   `base` (`agents-v2`, [Launch requests](terminal-launch.md#catalogue-and-named-bases-agents-v2))
   the worktree starts from that branch's commit instead of HEAD.

If the add fails, the connector removes only what this same call created:
`git worktree unlock <destination>`, then `git worktree remove --force
<destination>` (only if git lists it; otherwise it removes the destination only if
it is an empty folder), then `git branch -D <branch>` (only if the branch now
exists and did not before). If the create is refused after a successful add (for
example consent was withdrawn, or tmux failed and lists no such session), the same
call runs `git worktree remove --force <destination>` and
`git branch -D <branch>`; a worktree it adopted rather than made is never removed.
These are the only uses of `--force` and the only branch deletions; the branch name
contains the run token, so it cannot be anyone else's branch.

### Status

In the worktree:

1. `git rev-parse --show-toplevel` (must be the worktree itself) and
   `git rev-parse --git-common-dir` (must be the `.git` folder of a normal,
   non-bare repository whose name slugs to `repo`).
2. `git worktree list --porcelain`, which must name that repository first and the
   worktree exactly once, not prunable or bare.
3. `git status --porcelain=v1 -z --untracked-files=all --ignore-submodules=none`.
   The two extra flags override repository settings such as
   `status.showUntrackedFiles=no` and `diff.ignoreSubmodules=all` that would
   otherwise hide files a remove would delete.
4. `git symbolic-ref -q HEAD`, then
   `git rev-list --count HEAD --not --remotes --exclude=<run branch> [--exclude=<HEAD's branch>] --branches`.
5. `git for-each-ref --format=%(objectname) %(objecttype) %(refname) refs/worktree refs/bisect refs/rewritten refs/stash`,
   then `git rev-list --count HEAD <tips> --not --branches --remotes --tags <stash>`,
   where `<tips>` are the commits held by `refs/worktree/*`, `refs/bisect/*` and `refs/rewritten/*`
   (refs that live in the worktree and go with it) and `<stash>` is what
   `refs/stash` holds (shared, so it survives a remove). More than 1,000 such tips
   marks the check incomplete.
6. `git ls-files -v -z`.
7. A walk of the worktree folder (below).

### Removing

Status is computed again, then, only if nothing blocks it, in the repository root:
`git worktree remove <worktree>`, **without** `--force`, on a 30-second budget of
its own (not what the checks left of theirs; the checks share 30 seconds, so a
remove takes at most a minute), which the end of the connection does
not cut short, so a remove that has started is never stopped half way. git checks cleanliness and
locks once more itself. `branch` and `prune` are never run.

### Hooks and repository configuration

The repository's hooks are disabled for the add by `-c core.hooksPath=/dev/null`
(a test with `post-checkout`, `reference-transaction` and `post-index-change`
hooks, in `.git/hooks` and in a configured hooks folder, shows none runs). The
read-only commands and `worktree remove` do not run hooks.

This does **not** mean that making or checking a worktree runs no repository-
configured program. The repository's own configuration still applies: a smudge or
clean filter (for example git-lfs), `core.fsmonitor`, and similar settings can run
programs during the add's checkout and during `status`. That configuration is the
user's own local setup, not content that came with a clone, but it is code. The
fixed command lines above rule out adding further `-c` overrides. The agent
started afterwards can run anything the user can, as it always could.

## Limits and budgets

- Each git call is limited to 60 seconds. All the calls for one create or one
  status share a single 60-second budget. A remove's checks share 30 seconds and
  its `git worktree remove` has a separate 30, so a remove takes at most 60. Cleanup after a failed add
  has its own 30-second budget.
- On timeout the whole process group git started is killed (SIGKILL), and the
  process is waited for at most 2 more seconds. A helper that puts itself in a new
  session or process group (a daemonizing fsmonitor, for example) escapes that.
- Output is capped at 4 KiB per call, except `worktree list`, `status`,
  `ls-files` and `for-each-ref`, which are capped at 4 MiB; anything beyond is discarded while
  reading. This departs from the 4 KiB limit in the plan's constraints on purpose:
  `worktree list --porcelain` passes 4 KiB at around 17 worktrees, and a cut
  listing would make adoption and removal refuse a perfectly good worktree. A
  listing that reaches 4 MiB is never trusted: adoption answers `git_failed`
  ("git listed too many worktrees to read"), locating answers `not_registered`, and
  `ls-files` marks the check incomplete. A `status` listing cut at 4 MiB makes the
  changed count a lower bound; any count above zero blocks removal anyway.
- The walk never follows symlinks and stops after 200,000 entries or below a depth
  of 256. Below the worktree's own top-level `.git` file, any entry named `.git` in
  any letter case or ending in `.git` (file, folder or symlink), or any folder laid
  out like a git directory (`HEAD`, `objects` and `refs`), marks it as containing
  another repository. Going past a cap, a folder that cannot be read, or the end of
  the request's budget marks the check incomplete.
- The controller waits up to 180 seconds for a worktree create, status or remove
  (10 seconds for every other control call): a create can take 90 seconds on the
  machine and a remove queued behind it 60 more.
- The connector answers the controller's health probes on its reader and hands
  every other control message, in order, to one dispatcher over a bounded queue
  (64). A worktree status or remove then runs on its own goroutine, so the
  dispatcher and the probes never wait for git. One worktree status or remove runs
  at a time per machine: a second is answered at once with `conflict`, which the
  API reports as 409 `worktree_busy`, "That machine is already working on a
  worktree. Try again in a minute." A worktree create still runs on the
  dispatcher, as every create does, so the machine's next session operations wait
  for it (probes do not). A remove holds the manager lock, so a create or end
  arriving during a remove waits for it.
- **While a worktree create runs, that machine's other terminal work waits.** The
  create occupies the dispatcher, so everything else for that machine queues
  behind it: other creates and ends, worktree status and remove, and attachment
  renewals. An open terminal renews its attachment every 5 seconds and gives up
  after 10, so open terminals on that machine may detach during a slow create, and
  during a remove that waits behind one; the person reattaches afterwards. Probes
  are still answered, so the machine is not marked unreachable.
- The dispatcher's queue holds 64 messages. The controller gives up on an ordinary
  call after 10 seconds while the message may still wait in that queue, so retries
  during a slow create can fill it. A request that finds the queue full is answered
  `unavailable` at once by the reader (a `result` or a `worktree_result`), the
  connection is kept, and the queued requests are still handled in order.
- Before this change the connector ran every request on the reader itself, so a
  worktree request that ran for longer than about a minute and a half could leave
  three probes unanswered, and the controller would mark the machine unreachable
  and disconnect it.
- When the connection ends, a running status is cancelled (git is killed) and
  answers nothing; the connector's cleanup waits for it.

## What the counts mean

- **changed**: entries in the status listing: modified, staged, deleted, renamed or
  copied (counted once) and untracked files, including every file in an untracked
  folder. Ignored files are not counted. `paths` holds the first 20, each at most
  255 bytes, with control, format and invalid characters replaced by U+FFFD.
  File contents are never read.
- **unpushed**: commits reachable from the worktree's `HEAD` that are on no
  remote-tracking branch and on no local branch other than the run's branch and
  the branch checked out in the worktree. In a repository without a remote this is
  the commits made in the worktree since it was created, provided the branch it
  was made from still holds its starting commit (otherwise it over-counts, the safe
  direction). These commits stay on the run's branch after a remove.
- **unreferenced**: commits reachable from `HEAD` or from the worktree's own
  `refs/worktree/*`, `refs/bisect/*` and `refs/rewritten/*` that no branch, tag, remote-tracking branch
  or stash holds (work on a detached `HEAD`, for example). A remove would leave
  them unreachable.
- **hidden**: files git is told not to check: assume-unchanged, or skip-worktree
  and present on disk (a skip-worktree file that is absent, the usual case outside
  a sparse checkout, holds no edit). git cannot say whether they were edited.
- **nested**: another repository or worktree lies inside, perhaps ignored.
- **incomplete**: the check could not cover the whole worktree.

## What a remove deletes

A remove deletes the worktree folder and everything in it, **including ignored
files** such as `.env`, `node_modules` or build output. It does not delete the
branch, so committed work stays. The empty `~/.reet/worktrees/<project>/<repo>`
folders are left behind.

A remove is refused, and nothing is touched, when:

| Condition | Code | HTTP | Sentence |
| --- | --- | --- | --- |
| The counts differ from the ones the person was shown, in either direction | `worktree_changed` | 409 | That worktree changed since you looked. Check again. |
| `changed` is above zero, even when it was shown | `has_changes` | 422 | This worktree has changes you haven't saved. Commit, stash or discard them in the worktree, then check again. |
| `hidden` is above zero | `hidden_changes` | 422 | Git is not tracking some edits in this worktree. Review them before removing. |
| `unreferenced` is above zero | `unreferenced_commits` | 422 | Some commits in this worktree are not on any branch. Put them on a branch first, then check again. |
| Another repository is inside (ignored ones included) | `nested_repository` | 422 | This worktree contains another git repository. Move or remove it first. |
| The check was incomplete (for example more than 200,000 entries) | `check_incomplete` | 422 | reet couldn't check all of this worktree. Remove it yourself. |
| git refused (a lock, for example) | `git_failed` | 422 | Git couldn't remove that worktree. (`detail`: git's first line) |

The checks run in that order. Only `unpushed` can be shown and then removed with:
those commits stay on the branch.

## Refusals and sentences

Create (`POST /api/v2/terminal/sessions` with `worktree` and `project`):

| Reason | Code | HTTP | Sentence |
| --- | --- | --- | --- |
| Machine lacks `worktree` | `worktree_unsupported` | 409 | Update reet on that machine to start agents with worktrees. |
| Not the top of a normal repository: a `.git` file, a bare repository, a subfolder, a symlinked `.git`, a `core.worktree` elsewhere, a plain folder, home itself, or a `HEAD` with no commit yet | `not_repo_root` | 422 | That folder isn't the top of a git repository. |
| Merge, rebase, cherry-pick, revert, bisect or sequencer in progress | `repo_busy` | 422 | That repository is in the middle of a merge, rebase or similar. Finish or abort it first. |
| The destination or branch exists and is not this run's | `worktree_exists` | 422 | A worktree or branch with this run's name is already on that machine, so nothing was started. |
| git failed or is missing | `git_failed` | 422 | Git couldn't make a worktree there. (`detail`: git's first line, plain text, at most 200 bytes) |
| `~/.reet/worktrees` is a link, another user's, or writable by others | `outside_home` | 422 | The folder ~/.reet/worktrees on that machine is a link, belongs to another user or can be changed by others. Fix it, then try again. |
| A refusal with no recorded reason (a create refused before reasons were stored) | `worktree_refused` | 422 | That machine refused to make a worktree for this request. Start it again to see why. |

The folder and tool refusals of a launch (`folder_unavailable`,
`tool_not_installed`, `prompt_unsupported`) apply unchanged.

Status (`POST /api/v2/terminal/worktrees/status`) and remove
(`POST /api/v2/terminal/worktrees/remove`) also answer:

| Reason | Code | HTTP | Sentence |
| --- | --- | --- | --- |
| The machine is already running a worktree status or remove | `worktree_busy` | 409 | That machine is already working on a worktree. Try again in a minute. |
| The machine answered but could not do it (unavailable, failed, capacity) | `worktree_unavailable` | 503 | That machine couldn't do that just now. Try again in a moment. |
| Nothing is at the path (never made, or already removed) | `not_found` | 404 | That worktree isn't on that machine. It may have been removed already. |
| Something is there, but git does not list it as this repository's worktree | `not_registered` | 422 | Git doesn't list that folder as this run's worktree, so reet won't touch it. |
| A folder on the way is a link, another user's, or writable by others | `outside_home` | 422 | (as above) |
| git failed during status | `git_failed` | 422 | Git couldn't check that worktree. |

A reason a request cannot normally produce gets that request's general sentence
with code `worktree_refused`.

## The API

All three routes are account-mode browser routes with the same checks as every
other terminal route: a signed-in account session (no API, MCP or legacy tokens),
not a viewer, the canonical `Origin`, the remote-terminals switch on, strict JSON
(unknown fields and trailing data refused) and `Cache-Control: no-store`.

- `POST /api/v2/terminal/sessions` accepts `worktree` (a run token string, not a
  switch) and `project` beside the launch fields.
- `POST /api/v2/terminal/worktrees/status` takes `{agentId, project, repo, run}`
  and answers `{path, branch, changed, unpushed, paths, unreferenced, hidden,
  nested, incomplete}` with every field present.
- `POST /api/v2/terminal/worktrees/remove` takes the same plus `changed` and
  `unpushed`, both required. The controller sends the remove; the machine
  computes status again and decides, and its `ok` answer names the folder it
  deleted and the branch it kept. It answers `{ok: true, path, branch}`.
  If the remove was sent but no answer came, the controller asks for status
  once: if nothing is there any more, it answers `{ok: true, branch,
  confirmedBy: "status"}` (the folder is not known then); otherwise it answers
  503 as a reconnect, and the person checks again.

The session JSON returned by create (and listed by `GET /api/v2/terminal/sessions`)
carries `worktreePath`, `worktreeRepo` and `worktreeBranch` for a session started
in its own worktree. `repo` in status and remove must be that `worktreeRepo`, the
name the machine used, not a name recomputed from the saved folder: when the
member folder is itself a symlink inside home, its own name differs and status
answers `not_found`. A refused create's reason and detail are stored with the
request, so a retry of the same request reports the same refusal.

## Idempotency and adoption

The whole `Create`, worktree fields included, is the idempotency key, as for a
launch. The same request id with the same fields returns the same session and
starts nothing; a changed run token or project on the same request id is a 409.

On the machine, a create whose run token already has a worktree **adopts** it
instead of refusing, but only when git lists exactly that path, on exactly that
branch, not locked, not prunable and not detached; anything else that exists is
refused as `worktree_exists`. Adoption runs no command that changes anything, and
a later failure never removes an adopted worktree.

Adoption does not depend on the request id. A create with a **new** request id and
the same run token adopts the worktree and starts a second agent in it. The
Projects run must therefore derive one request id per member and reuse it for every
retry whose outcome is unknown, and use a new request id only after a definite
refusal (when no agent was started).

The run token is derived per member (from the run and the member's position), never
one token for a whole run: two members on one machine whose folders are the same
repository then still get separate worktrees and branches. The Projects run takes
the repository name for status and remove from the create reply's `worktreeRepo`,
never recomputing it from the saved folder. Members with the same machine and the
same folder were refused as a duplicate repository when the Project was saved
(saved Projects can no longer be changed) and are refused when a run starts; two different saved folders that resolve to one repository on the machine
are not caught by the controller.

## Starts from Home's launch bar

Home's launch bar ([Start an agent session](start-agent-session.md#on-home-the-launch-bar)) asks for
a worktree whenever its sentence says **in a fresh worktree** (the project's worktree choice, else the
account's). The base:

- **One project.** `base` is sent only when it was chosen: by the person in the Branch slot, by the
  project's base branch or by the account's default base branch. Otherwise nothing is sent and the
  worktree starts from the checkout's HEAD; the sentence names that branch as the machine reported it.
- **Branch listing.** The Branch slot's names come from the machine
  (`GET /api/v2/machines/{agentId}/branches`, [Folder browse and branch listing](folder-browse.md)),
  at most 200, filtered by the machine. A name only suggested from that list is never sent unless the
  person picks it.
- **Several projects** (Select, 2 to 12). Each member's create carries its own project's base branch,
  else the account's default, else none; the one-project choice is never applied to all of them.
  The run is a selection run (`origin: selection`) and its members follow the orchestration below.

## The run orchestration

Projects PR 2 adds the controller code that starts a run (`internal/projectrun`):

- Each member's create carries the request id `run|position|attempt` (SHA-256, the
  first 48 hex characters) and, when the Project uses worktrees, the run token
  `worktree|run|position` (the first 24) and the Project slug of the run's name
  snapshot.
- The member is durably marked *sent* just before its create is handed to the
  broker. The mark is cleared only when that request id is known to have started
  nothing. A retry reuses the attempt (the same request id) while the mark is set,
  and takes the next attempt only when it is clear, so a retry never adopts the
  worktree under a new request id and starts a second agent.
- The broker answers a request id it already reserved from that reservation, before
  it looks at the machine's capabilities, so a replay after a capability change
  still returns the existing session.
- At most two members of a run, and one create per machine across all runs, are
  in flight at once. A member whose machine is not ready waits for it (30 seconds,
  or 2 minutes after a controller restart) without holding a slot. A run of 12
  members on one machine therefore takes at most about 12 times the worktree create
  limit (3 minutes each), about 36 minutes, in the worst case.
- Starting a run needs a request id; repeating it answers with the same run. A new
  run of a Project is refused while an earlier one still has pending members.
- The run JSON names each worktree for status and remove: `host` (the machine's
  agent id), `worktreeProject`, `worktreeRepo` (as the machine reported it) and
  `worktreeRun`. A successful remove moves that member to `removed`.
- A run without worktrees starts each agent in the saved folder itself; its members
  say `sharesCheckout`, because any other run or session there shares that checkout.
- A member's machine is its enrollment (agent id). Merging or revoking a machine
  does not rewrite saved Projects or runs: members of the old enrollment then fail
  `unknown_machine` (nothing is sent). A saved Project can no longer be edited (410
  `projects_moved`); its folder project is moved to the remaining machine instead.
- The controller is single-process: claims and per-machine slots are in memory.

## Audit

- `terminal-launch` (existing) gains, for a worktree launch, `worktreeRun` (the run
  token), `project`, `branch` and `worktree` (the folder the machine reported). If
  the create's reply was lost and the session was resolved later, `worktree` is
  absent. The prompt is never included.
- `worktree-remove`, source `ui`, with exactly `machine`, `host`, `path` and
  `branch` from the machine's `ok` answer. A refused remove writes nothing. When
  the answer was lost and status then found nothing there, the event has
  `machine`, `host`, `branch` and `confirmedBy: "status"`, without `path`. An
  `ok` that arrives after the controller gave up on the call is still audited,
  with `late: "true"`, from the answer. If the connection is lost before the
  controller hears the result, the removal may not be audited: the answer can only
  come over the same connection.
- The controller checks what the machine reports: a create's folder must be the
  run's folder under `~/.reet/worktrees` and a remove's folder and branch the
  requested run's. Otherwise nothing is recorded or audited and the API answers
  503 `worktree_mismatch`, "That machine's answer did not match the request. Check
  again." For a create the agent may already be running; its session is listed
  without a worktree folder.

## Known limits

- Nothing has been run on macOS outside CI. The tests resolve `/tmp` symlinks and
  do not depend on the shell's name, but the process-group kill, the porcelain
  output of the macOS git and the APFS file names are covered only by CI.
- An agent still running in the worktree is not checked. A remove that passes every
  check deletes the folder under it (its uncommitted work is still protected by the
  checks, and its commits by the branch). The page should offer *Remove worktree*
  only for sessions that have ended.
- Helpers that daemonize escape the process-group kill on timeout.
- If a worktree create's reply is lost entirely (the connection drops), the
  controller learns the session's state by reconciling, which does not carry the
  worktree's folder, so the session has no `worktreePath`. A reply that only
  arrives late is still recorded.
- A same-user process could change the folders between the checks and git's own
  remove; same-user attackers are out of scope. A nested repository created between
  the walk and `git worktree remove` is not seen.
- A worktree of a different repository with the same folder name, placed at the
  path by hand, passes the checks; the protocol carries the repository's name, not
  its path.
- While a worktree create runs, that machine's other session operations wait for
  it (up to the budget); probes are still answered.
- Windows is not supported.

## What this does not establish

A started worktree session means only that the connector made the worktree and
branch and then started the program in tmux in that folder. It does not establish
that the agent is signed in, understands the prompt, or makes progress; that the
branch contains anything; or that the repository's hooks, filters, build or tests
are safe to run. A status shows what git and the walk reported at that moment, not
