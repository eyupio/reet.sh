## Implemented first checkpoint

`POST /api/v2/library/deployment-intent` is an authenticated connector request using the existing private-content account/role, personal-token/origin and enrollment-key guards. Its flat JSON request contains `targetId`, `bindingId`, `itemId`, `revisionId` and optional `generation`.

The store checks one transactional snapshot of the active enrollment, target ownership and canonical selection, exact existing revision pin, canonical status, content and deletion state. It returns `generation`, `action`, `reason`, `name`, `revisionId`, `digest`:

- `maintain` / `selected_in_use`: selected In use skill with usable canonical contents.
- `remove` / `inactive`, `deselected` or `library_deleted`: explicit central control intent, never inferred from a missing local file.
- `blocked` / `content_unavailable`: retain local bytes while a selected item has unavailable/unsupported contents or another content problem; do not turn incomplete metadata into deletion permission.

The generation hashes the account, enrollment, target, binding, pinned base, durable selection version and item version/status/deletion/content fields. Re-submit the observed generation immediately before work and when acknowledging a result. A mismatch returns 409, including status/selection ABA changes back to the same visible value. Repeat reads without control changes return the same token. Foreign enrollment/target or unpinned bindings are refused. No new schema or database-format bump is introduced by this read contract.

**This is a controller intent snapshot, not a filesystem ownership grant or completed deployment receipt.** The existing pin protects recoverable revision bytes; it does not prove the connector owns an arbitrary local path. The connector must independently prove a managed local binding, containment, local consent and stable contents before any destructive action. The gated connector path below now calls this endpoint in its test harness; normal controllers do not advertise the capability yet, so normal operation remains additive and emits no restore notifications.

## Connector ownership continuation

The existing target executor now has a post-install verification hook, after the private installer's staging-directory rename succeeds. The pre-write hook still pins the exact revision and saves the edit base before the rename. A new local deployment journal entry records target ID, revision, digest and an initially false `verified` flag. Only the post-write hook can set that flag after checking enrollment identity, refreshed local consent, target/item/revision identity, safe directory ancestry and the installed bundle's exact digest. A failed download, refused pin, interrupted preparation, failed rename or changed post-write content cannot produce verified ownership. The journal survives restart through the existing private atomic-write path; there is no second executor or writer.

New imports explicitly mark their binding as a source. Importing an installed path clears its deployment ownership; subsequent sync cannot silently promote that source again. Existing legacy edit bases and adopted copies remain unowned, even if their bytes match a selected revision. They require the separate verified migration still listed below. Updating a known new deployment prepares a fresh unverified receipt; conflicting item or target identity is refused. These records establish local install provenance only: they are not controller operation acknowledgements, capability negotiation or permission to remove files.

The real executor tests cover successful install, pin refusal, interruption after preparation, a foreign entry appearing before rename, and local mutation before verification. Additional cases cover legacy/source preservation, an import racing verification, changed target/item/revision/enrollment/consent, and symlink substitution. No deletion or restore notification is emitted by this continuation.

## Gated managed-removal continuation

The existing target executor can now append explicit managed-removal actions to an otherwise additive plan. Each action carries the controller intent generation and exact target/binding/item/pinned revision, plus the observed local digest. Only verified target-bound installations directly inside that resolved target directory are candidates. Imported sources, legacy bases, unverified preparations, other targets and untracked extras remain untouched. Unavailable intent/content blocks that item in the plan instead of treating it as removed. A target snapshot that still desires the same item is refused as stale.

Apply refreshes local consent and enrollment identity, rechecks safe ancestry, exact local bytes and current intent, captures complete unseen local edits, and uses the existing recoverable backup helper. Partial missing bundles are not uploaded as central deletions: their surviving bytes are preserved intact in backup. The journal stores the backup destination and a `prepared` phase **before** rename. Immediately before moving it checks consent, contents and generation again; afterward it verifies the backup digest, local absence and current generation before recording `removed` and clearing installed ownership. Failed journal writes or unsafe backup links refuse the move. A stale post-move check leaves a prepared journal with the exact backup path and fails the job rather than acknowledging removal. No notification is sent.

This path requires an explicit `managedRemovals: 1` in the library-protocol response. Missing or unknown versions preserve additive behavior, and a new handshake clears a previous capability after controller downgrade. **The controller deliberately does not advertise it yet.** The HTTP test-controller/real-filesystem executor harness opts into it to exercise removal; this is not completed normal controller/connector acceptance or an enabled production feature. Automatic destructive-plan approval remains refused by the existing `additivePlan` guard. Do not weaken that guard: implement authoritative plan validation and acknowledgement fencing before advertising the capability.

Interrupted prepared operations currently require recovery; they are not blindly repeated. Exceptions during apply still stop that job, while unavailable items identified in planning allow other planned items through. Recovery, controller receipts, safe automatic approval and execution-time isolation of individual failures remain Stage 4 work. Source reimport and replacement of the local enrollment are tested fences. A replaced local enrollment is now also refused before edit negotiation/upload, adoption and installation, preserving its old pending bytes rather than using a stale in-memory enrollment. The current main including #679 (`f0ddfe4f`) is integrated without conflicts.

## Controller approval and acknowledgement fence (9 November 2026)

The controller now judges managed-removal plans itself instead of trusting the connector's `removalIntent`. `planRemovalVerdict` runs inside the job-result transaction when a machine reports an automatic plan. Every non-additive action must be an explicit removal for that job's target, with a matching item and a generation proof, and the controller recomputes current intent in the same transaction. The verdicts are:

- **Approved:** every removal is still `remove` at the submitted generation. The job becomes an approved apply, as additive plans already do.
- **Stale:** the generation differs (including status/selection ABA), the pin is gone, or intent is now `maintain` or `blocked`. The job fails and a fresh plan is requested; nothing is applied.
- **Review:** any other shape (missing proof, another target, a replace, an unknown action) keeps the existing "Removals need review" behaviour. The `additivePlan` guard is unchanged.

`removalAcknowledgementCurrent` repeats the check against the **stored approved plan** (not the connector's reported copy) when a successful apply result arrives. If the item was reselected or reactivated while the machine worked, the result is recorded as failed with a replan, never as a completed removal, so the next plan reinstalls it. The existing receipt/idempotency path and the single executor are unchanged.

`libraryDeploymentIntentTx` is the transaction-level form of the intent read; the endpoint's behaviour is unchanged.

**The capability is still off.** `Store.SetManagedRemovals` is an internal rollout control, set from `REET_LIBRARY_MANAGED_REMOVALS=1` in `cmd/reet/main.go` and defaulting to off. While off, `/api/v2/library/protocol` omits `managedRemovals` and the controller never approves a removal plan. It is not a user-facing setting and should stay unset until the remaining Stage 4 items below are done and proven with the real controller/connector harness.

Tests: store tests cover disabled (needs review), approved current removal, stale-at-approval, ABA generation, foreign target, missing proof, a superseded acknowledgement (reactivated mid-removal) and a current acknowledgement. An API test checks the capability is omitted by default, advertised when enabled and withdrawn again. These are controller-side checks with a store fixture; they do not run a connector against the real controller. No filesystem acceptance, interrupted-operation recovery, ownership migration, debounced restoration or notification is added by this checkpoint.

## Interrupted-operation recovery (9 November 2026)

A crash during a managed removal leaves a `prepared` journal that records the backup path and, now, the digest the entry had when the move was prepared (`libraryRemoval.Digest`, optional in the file format). `recoverLibraryRemovals` settles it at the start of the next plan for that target. It runs under the existing journal lock, before the capability check, so a controller downgrade cannot strand a journal. It never moves, copies or deletes content and needs no controller. It acts only on what the filesystem proves:

| Entry | Backup | Result |
| --- | --- | --- |
| present | absent | The move never happened. The journal is cleared and the entry stays a managed copy; ownership is re-proven before any later removal. |
| absent | present, digest matches the journal | The move completed. The journal becomes `removed` and installed ownership is released. Whether the item returns is decided by the next plan from current controller intent, never from this record. |
| present | present | Ambiguous. Everything is retained, the journal is kept and the item reports a problem. |
| absent | absent | Same: retained, journal kept, problem reported. |
| absent | present, digest differs, a link, or an old record with no digest | Same: retained, journal kept, problem reported. |

A held entry is skipped by planning (it plans no removal) and keeps its specific message; healthy entries continue. Re-running recovery changes nothing further.

Tests cover each row, idempotent re-runs, and recovery after a simulated controller downgrade. The existing removal matrix still passes. The sandbox runs as root, so `journal_refused` (which relies on a read-only directory) fails here exactly as it does on the previous commit; compiled and run as the non-root user `nobody`, the whole removal matrix, the recovery tests and the full scanner package under the race detector pass. The controller-side receipt for a removal that finished locally but failed to acknowledge is still the replan path above; no separate operation-receipt table was added.

Not done by this checkpoint: legacy ownership migration, per-item failure isolation at execution time, debounced restoration and notifications.

## Execution-time failure isolation (9 November 2026)

On a library (canonical) target the apply loop no longer stops at the first failed action. An item-scoped failure (a refused or stale intent check, changed ownership, a failed install, backup or verification) is recorded against its slug and the loop continues; the final rescan excludes those slugs, and the apply then ends with one error that names every failed item and says healthy items synced and the failed items' local files were left as they were. The job is therefore still reported as needing attention, never as a complete sync. Failures that affect the whole target still stop the apply immediately: withdrawn consent, a replaced or mismatched enrollment (now the shared `errLocalAuthorityChanged`), and context cancellation. Non-canonical targets keep the previous stop-at-first-error behaviour, and the pre-apply checks that detect a stale plan or changed local skills are unchanged and still refuse the whole apply.

A consequence worth knowing: because the apply now reaches its final verification after an item failure, interrupted-operation recovery can settle that same item's journal in the same run. In `stale_after_move` the move had completed and its backup matched, so the journal is now `removed` with the backup path recorded (previously it stayed `prepared` until the next plan); acknowledgement still failed, and the controller's replan decides whether the item returns. `edit_during_check`, whose backup differs from what was prepared, is still held as `prepared`.

Tests: a new fixture with two managed items where the first-sorted one fails its execution-time intent check proves the healthy one is still removed with an intact backup and the failure is named, and that withdrawing consent mid-apply stops the whole target with the healthy item untouched. The earlier removal matrix, recovery tests and the full scanner package pass under the race detector when run as a non-root user. As before, `journal_refused` fails when the suite runs as root because it relies on a read-only directory.

Not done: the failed-item message is returned through the existing job result; there is no per-item durable record or notification yet. Legacy ownership migration, debounced restoration and notifications remain.
