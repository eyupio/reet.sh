# Projects Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Save a named set of repository folders (machine plus folder) with a default agent and model, start one agent session in each with one confirmed action, and give each run its own git worktree that reet never removes by itself.

**Architecture:** Worktree creation, status and removal are a negotiated extension of the private terminal protocol (`worktree-v1`), run by the connector with fixed git argument vectors. The controller stores Projects, members and runs, and orchestrates a run by calling the existing launch create path per member with derived, idempotent request ids. The web adds a pure `projects.ts`, a Projects page, a Project page, and dialogs.

**Tech Stack:** Go 1.27.1, git, tmux 3.2+, SQLite store, Svelte 5 runes + TypeScript in `web/` (build before Go tests), Node 22, Playwright fixtures.

**Spec:** `docs/superpowers/specs/2026-10-25-projects-design.md` (read it; the plan argues from it). The shipped building blocks are described in `docs/terminal-launch.md` and `docs/start-agent-session.md`.

## Global Constraints

- Never name competing products in repo docs or UI. "verified" and "healthy" never describe a machine, session or worktree; "started" means the connector started the program in tmux in that folder.
- Voice: plain exact wording for states, errors and confirmations; at most one light Yorkshire phrase in a heading, lede or success line.
- Limits: Project name 1–80 characters, unique per account (case-insensitive); at most 50 Projects per account; at most 12 members per Project, each machine plus folder at most once; shared prompt follows the opening-prompt rules (≤2,000 bytes, valid UTF-8, no control characters except newline, not starting with `-`); member `dir` validated exactly as `terminalproto` validates `Dir`; at most 2 members in flight per run; runs list shows the newest 20.
- `terminalproto.Create` stays a comparable struct; the new field is a flat `string` with `omitempty`: `Worktree` (lower-case hex run token, 16–48 characters). Feature token `worktree-v1`; capability `worktree` (omitempty, requires `launch`). No protocol version bump. A peer without it is never sent worktree fields.
- Git is run only as an argument vector (never a shell) with a minimal environment (`HOME`, `PATH`, `LANG`; every `GIT_*` removed), `-c core.hooksPath=/dev/null` on the create, a 60-second timeout and output capped at 4 KiB. The only git commands reet runs: the `worktree add`, the status/count reads, and `worktree remove` **without `--force`** (the one `--force` allowed is cleaning up a worktree the connector itself created in the same failed call). Branches are never deleted except one the connector created in the same failed call.
- Worktrees live only under `~/.reet/worktrees/<project-slug>/<repo-name>/<run-token>`, branch `reet/<project-slug>-<run-token>`; slugs are `[a-z0-9-]`, no dot-segments or separators.
- The prompt is never written to audit, logs, errors or browser storage; Projects data never goes into browser storage; only Project and run ids appear in URLs.
- Platform: Linux and macOS only; tests must not assume the shell is `sh`, must resolve `/tmp` symlinks, and CI runs the real-git tests on both.
- Build the frontend before Go checks; tmux and git on PATH; attribution trailers on commits.

## Review Focus

- A repository whose `.git` is a file, a bare repository, a detached HEAD during a rebase, or one with a merge in progress is refused with a plain reason and nothing is created.
- A repository's `post-checkout` hook never runs during creation (test with a hook that writes a marker).
- A retried create for the same run token adopts the worktree it already made (never a second worktree, never a duplicate branch); a different repo or path with the same token is refused.
- Remove refuses when the counts shown to the person no longer match, for a path git does not list, for a path outside `~/.reet/worktrees`, and never uses `--force`.
- A run interrupted by a controller restart resumes only members still `pending`; a started member is never started again; a retry after an unknown outcome reuses the derived id, after a definite refusal uses a new attempt id.
- Renaming or deleting a Project never changes its historical runs; deleting a Project with worktrees still present is allowed but says the worktrees remain.
- Per-machine (8) and per-account (32) session limits are shown on the confirmation sheet before Start, and a run that hits them mid-way marks the rest `failed` with the session-limit sentence.

## Parallel workstream — landscape review (added at the product owner's request)

Not a code task and not part of any Projects pull request. After PR 2 merges, run a structured review of
comparable open projects the product owner names (the sources are supplied in the session and recorded in
that pull request's description, not in this repository), comparing what each offers against reet.sh's
intended capabilities: multi-machine sessions, agent and skill and MCP syncing, Start an agent session,
Projects and worktrees, the planned chat layer, sandboxing, remote access and privacy posture, installation
and packaging, and cost and health visibility.

- Read each project's documentation pages and repository, not only its landing page; note where a page is
  silent so a gap is never asserted from silence.
- Produce a comparison the product owner can read (a private artifact), a ranked list of capabilities worth
  adding with the reasoning, and which already conflict with a decision recorded in the handoff (for example
  permission-bypass switches and free-form command lines, which reet.sh deliberately does not offer).
- Accepted items go to the handoff roadmap in neutral wording; competitor names stay out of repository docs
  and the UI.
- Questions to settle with the product owner (via the usual decision prompts) before any item becomes a
  design: priority order and whether it displaces Projects PR 3 and PR 4.
